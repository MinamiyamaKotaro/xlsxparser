# `PoC/`

使い捨ての検証・探索用コードを置く場所。**このディレクトリの中身(この`README.md`を除く)は一切コミットされない**(`.gitignore`で`/PoC/*`を除外し、`README.md`だけを明示的に追跡対象に戻している)。

## いつ使うか

- 設計上のオープンクエスチョンを、実装に進む前に手を動かして検証したいとき(例: OOXMLの座標変換アルゴリズムが実データで成立するか確認する)
- 実際のExcel/LibreOffice出力を生成・解析して、仕様の未確認点を調べたいとき
- アルゴリズムの正しさ・計算量・エッジケース耐性を、本体コードに組み込む前に独立して検証したいとき

「設計→実装→テスト」の順で進めるプロジェクト方針([[feedback_process_design_first]])における、実装着手前の検証フェーズをこのディレクトリで行う。ここでの検証結果はGitHub Issue/PRのコメントとして記録し、コードそのものはリポジトリに残さない。

## フォルダ命名規則

対象のGitHub Issue番号を用いて `issueNNN-poc/` とする(例: `issue67-poc/`)。1つのIssueに対して複数回検証する場合も同じフォルダを使い回してよい。

## 運用ルール

- 中身は`.gitignore`で除外されているため、**コミットする必要も、コミットされる心配もない**。気兼ねなく使い捨てて構わない。
- 検証結果(数値・結論)は、当該GitHub Issueへのコメントとして記録する。PoCコード自体をリポジトリに残す・PRに含めることはしない。
- 本体クレート(`xlsxparser`)への依存が必要な場合は、`path`依存で参照するか、検証に必要な最小限のロジックだけを独立して再実装する(本体を汚さないため)。
- 外部ツール(LibreOffice等)を使った検証を行った場合、再現に必要な手順(スクリプト・マクロ等)は当該フォルダ内に残しておくと良いが、リポジトリには含まれない前提であることを踏まえ、重要な知見は必ずIssueコメント側に転記すること。
