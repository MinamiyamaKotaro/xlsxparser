# Test suite overview

This directory implements the five fixture categories proposed in
[Issue #28](https://github.com/MinamiyamaKotaro/xlsxparser/issues/28) —
**normal** (正常系), **error** (異常系), **complex** (正常系・複合型),
**load** (負荷), and **security** (セキュリティ) — plus a parallel set of
unit tests embedded in `src/` (`330`+ `#[test]` functions as of this
writing, run via `cargo test --lib`). This file is a map of what's
covered, and — in [Edge-case coverage audit](#edge-case-coverage-audit) —
an explicit record of what isn't, so gaps don't have to be rediscovered
from scratch each time someone asks "is X tested?"

## Layout

Each category has two parallel test binaries:

- `tests/<category>.rs` — the `#[test]` functions, driving in-memory
  `.xlsx` packages built on demand by `tests/fixtures/<category>.rs`
  (via `tests/fixtures/builder.rs`'s `build_zip`/`rels_xml`/`workbook_xml`/
  `worksheet_xml` helpers). Nothing here is a binary file committed to the
  repo — every fixture is hand-authored XML, so a fixture's exact shape is
  reviewable as a diff, not opaque bytes (`tests/fixtures/builder.rs`'s
  module doc has the full rationale, including why this matters
  specifically for the `security` category: a committed `.xlsx` there
  would mean carrying live zip-bomb/zip-slip/XXE payloads as repository
  bytes).
- `tests/real_<category>.rs` (normal/complex/load/error only — security
  has no real-file counterpart) — the same scenarios, but against actual
  files generated by `openpyxl` (`scripts/generate_real_fixtures.py`),
  committed under `tests/fixtures/<category>/*.xlsx`. These exist because
  a hand-authored fixture only ever exercises the *author's* understanding
  of the format; a genuine third-party writer can differ in ways that
  matter (see `tests/real_fixtures.rs`'s module doc for a concrete example
  this caught: openpyxl's package-absolute worksheet relationship targets).

Unit tests (`src/**/*.rs`, `#[cfg(test)] mod tests`) cover the same
material one layer down — parser/resolver internals in isolation, without
going through a full ZIP package — and are generally where the exhaustive
boundary-value cases live (off-by-one row/col limits, malformed attribute
values, etc.), while the integration tests above verify the pieces wire
together end to end.

`tests/fixtures/other/` (`.gitignore`d, not part of this repo) holds a
larger ad hoc corpus of real-world files — currently sourced from
[calamine](https://github.com/tafia/calamine)'s test corpus — used to
*discover* compatibility gaps by diffing xlsxparser's output against
calamine's, cell by cell (see
[Issue #52](https://github.com/MinamiyamaKotaro/xlsxparser/issues/52)).
Every gap found this way that warranted a fix got a hand-authored,
committed regression test reproducing the same shape (e.g.
`tests/fixtures/normal.rs`'s `workbook_at_package_root`/
`cells_without_r_attribute`, added for
[Issue #55](https://github.com/MinamiyamaKotaro/xlsxparser/issues/55)/
[#79](https://github.com/MinamiyamaKotaro/xlsxparser/issues/79)) — the
real file is what *found* the bug, but the committed test is what
*prevents its regression*, since the corpus itself isn't part of CI.

## Coverage by category

- **Normal** (`normal.rs` / `real_normal` via `real_fixtures.rs`): every
  `CellValue` type, shared strings, inline strings, `t="d"` ISO 8601 dates,
  wrap text / font / alignment / number format / fill color styles, column
  widths, `date1904`, and (Issue #55/#79) packages whose workbook part
  isn't at the conventional `xl/workbook.xml` path or whose cells omit the
  optional `r` attribute.
- **Error** (`error.rs` / `real_error.rs`): truncated/syntactically invalid
  worksheet XML, a dangling sheet relationship, an out-of-bounds shared
  string index, overlapping/reversed `<col>` width ranges, and a reversed
  `<mergeCell ref>` — each asserted to return the matching `Error` variant
  rather than panicking.
- **Complex** (`complex.rs` / `real_fixtures.rs`): a merged region resolved
  transparently across every coordinate it covers, all four sheet
  visibility states (including an empty sheet) enumerated together,
  embedded images (single-cell and two-cell anchors, grouped/rotated,
  hyperlinks), and the extreme-sparse shape (`A1` + `XFD1048576`, Excel's
  actual opposite corners) that motivates the sparse `HashMap` storage
  model in the first place.
- **Load** (`load.rs` / `real_load.rs`): 300,000 cells in a fully-packed
  10,000×30 block, 1,000 sheets in one workbook, and a 50,000-entry shared
  string table — each a scale/resource-exhaustion check, not a
  correctness check.
- **Security** (`security.rs`): Zip Bomb (both the per-entry and
  cumulative-size caps), Zip Slip path traversal, XXE external-entity
  rejection, and the merged-region bounding-box amplification fixed by
  [Issue #43](https://github.com/MinamiyamaKotaro/xlsxparser/issues/43).

## Edge-case coverage audit

Assessed 2026-08-20, prompted by a request to gauge coverage of edge
cases beyond Issue #28's original five categories: extreme sparsity,
dense merged cells, "medium" density, Unicode/RTL text, and corrupted
OOXML. Findings below; update this section (status, evidence, date) as
gaps get closed or new ones are found — don't let it silently go stale.

| Area | Status | Evidence |
| --- | --- | --- |
| Extreme sparsity | ✅ Covered | `complex.rs`'s `extreme_sparse_coordinates_register_only_the_populated_cells` / `real_fixtures.rs`'s `real_extreme_sparse_xlsx_registers_only_the_two_populated_cells` — `A1` and `XFD1048576` (row 1,048,576, column 16,384: Excel's actual maximum in both dimensions), asserting only 2 entries ever land in the coordinate map. |
| Dense merged cells | ⚠️ Gap | The only merge-heavy fixture, `houganshi_merged` (both the hand-authored and `openpyxl`-generated versions — see `scripts/generate_real_fixtures.py`'s `houganshi_merged()`, whose own comment calls it "the grid-paper Excel shape from Issue #28"), contains exactly **one** merged region (`A1:C3`). Issue #28's original spec called for merges "至る所に" (everywhere); what's actually committed doesn't exercise that. `resolve::merge`'s unit tests (`region_count_at_the_limit_is_accepted`, `MAX_MERGE_REGIONS = 20_000`) do register many regions, but as a uniform 1×2-stacked-by-row pattern sized for the count/performance cap, not a realistic checkerboard-style dense arrangement verified end to end (JSON `rowSpan`/`colSpan` output included) at scale. |
| "Medium" density | ❌ Undefined | No fixture exists between the two extremes currently tested: `extreme_sparse` (2 populated cells) and `massive_dense_accounting` (300,000 cells, 100% fill within a fixed 10,000×30 block). There is no fixture representing the shape most real business spreadsheets probably have — a wide coordinate range with cells scattered at partial (e.g. 10-30%) density, exercising the sparse `HashMap` model's actual sparse case rather than either a handful of cells or a fully-packed rectangle. |
| Unicode / RTL text | ⚠️ Untested (verified working) | Every committed fixture's non-ASCII text is exactly one string, `"日本語Text"` (CJK, left-to-right) — see `tests/fixtures/normal.rs`'s `basic_types`. No fixture exercises RTL scripts (Arabic, Hebrew), emoji with ZWJ sequences, combining diacritics, or astral-plane/surrogate-pair characters. Manually verified (not committed) that all of the above round-trip correctly today through `parse_workbook_reader` → JSON, consistent with the pipeline relying on Rust's UTF-8-safe `String` throughout rather than manual byte slicing — so this is architecturally low-risk, but a future change to `parse/mod.rs`'s text-reading path has no regression test to catch a multi-byte-handling break. |
| Corrupted OOXML | ✅ Mostly covered, minor gaps | `error.rs`/`real_error.rs` (truncated/malformed worksheet XML, dangling relationships, out-of-bounds SST index, invalid column-width/merge ranges) + `security.rs` (zip bomb, zip slip, XXE) + `src/lib.rs`'s `corrupt_xlsx_errors_propagate_unchanged` (non-ZIP garbage bytes) + `src/container/mod.rs`'s `open_reader_rejects_corrupt_zip_bytes` + `src/pipeline.rs`'s `malformed_worksheet_rels_xml_propagates_parse_error`/`malformed_drawing_rels_xml_propagates_parse_error` (malformed `_rels` XML) + `src/parse/mod.rs`'s invalid-UTF-8-in-`<t>`/CDATA tests. Gap: only `xl/worksheets/sheetX.xml` has a dedicated malformed-XML-syntax fixture — `xl/workbook.xml`, `xl/styles.xml`, and `xl/sharedStrings.xml` bodies (as opposed to their `_rels` parts, which are covered) have no equivalent, even though they go through the same `convert_xml_error` path. |

Two related, already-triaged cases from Issue #52's own investigation are
*not* listed as gaps: `issue252.xlsx` (checksum-corrupted; both xlsxparser
and calamine fail on it) and `pass_protected.xlsx` (password-protected;
same) — both were judged out of scope since no reader can be expected to
open them.
