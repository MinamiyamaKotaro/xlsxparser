# `docs/design/` Security Review (2026-08-19)

This is a follow-up security review of every design doc under `docs/design/` (starting from [architecture.md](../design/architecture.en.md) and following every link — `lib.rs` / `error.rs` / `pipeline.rs` / `container/` / `parse/` / `model/` / `resolve/` / `json.rs`), as the tree stands today on `master`, following on from [`old/design-review.en.md`](old/design-review.en.md) (2026-08-17, pre-implementation) and [`old/code-review.en.md`](old/code-review.en.md) (2026-08-17, first code-level pass). Unlike the first review, `src/` is now fully implemented and has itself been kept in sync with the design docs through a "design → implementation → docs" process, including several feature waves the first review never saw: image anchoring and grouped images (Issues #65/#67), and font/wrap-text/alignment/number-format/fill-color resolution from `styles.xml` (Issues #37/#38/#41/#42/#75). This review focuses on what changed since 2026-08-17 — the three named threats' continued soundness across the newly added read paths, and new design-level risk patterns (algorithmic complexity, unchecked numeric fields, unresolved security-relevant Open Questions) in the material added since.

Findings below were cross-checked against `src/` where the design doc's own prose made a specific, checkable claim (e.g. "no cap exists," "this is O(1)"), including one direct empirical measurement (Finding 1). This is still fundamentally a design-doc review, not a full code audit — a parallel code-level review is assumed to cover `src/` line-by-line.

## Overall Assessment

The three threats named by the requirements spec — Zip Bomb, Zip Slip, XXE — remain soundly and *consistently* mitigated across every module added since the last review. `parse/drawing.rs` (drawing/grouped-image parsing) and `parse/styles.rs` (styles.xml parsing) both go through the exact same mandatory gateways every other `parse/` module uses — `create_secure_reader` for `Reader` construction, `read_event` for the DOCTYPE-rejecting XXE gate, `convert_xml_error` for Zip-Bomb-aware error conversion — and `pipeline.rs`'s new Phase 3.5 (image resolution) reads `drawingN.xml`/`drawingN.xml.rels` through the same `container::get_entry`/`parse::parse_relationships` gateways as every other OPC part, including re-validating an `Internal` image target's existence via `has_entry` before ever reading its bytes. No new read path bypasses any established gateway. The project's own prior finding shape — an O(N²) cost hiding behind a byte-size cap that doesn't actually bound the attacker-controlled count N (`docs/security/old/code-review.en.md` Finding 1, merge cells) — was evidently internalized: `resolve/column_width.rs` (Issue #39, added after that finding) cites `MAX_MERGE_REGIONS`'s reasoning explicitly and applies an equivalent defensive cap even though its own algorithm has no O(N²) risk, and `parse/drawing.rs`'s own `chExt=0` divide-by-zero guard is exactly the kind of numeric-safety check this review was asked to check for.

However, the same O(byte-size-cap-does-not-bound-attacker-controlled-N) pattern had reappeared, uncaught, in the material added by Issue #67 (grouped images) — this time as a *depth* rather than a *count*, and multiplicatively rather than quadratically. This was found, measured, and — following the exact same precedent as the original merge-cell finding — fixed immediately as part of this review cycle; see Finding 1 for the fix and re-measurement. A secondary, non-exploitable but real gap (Finding 2) is that several "Key Types" code blocks in `docs/design/` were not updated when the features their own prose/Dependencies/Testing sections describe were implemented, which is exactly the kind of gap that let Finding 1 go unnoticed by a documentation-based review until this cycle.

## Findings

### ~~Finding 1: Unbounded `<xdr:grpSp>` nesting depth in grouped-image resolution allows a CPU-exhaustion DoS well within every existing size/count limit~~ → **Resolved**

* **Severity: ~~High~~ → Resolved**
* **Location**: [`parse/drawing.en.md`](../design/parse/drawing.en.md), "Grouped images: `GroupContext` and `resolve_grouped_pic` (Issue #67)" section and its Open Questions 4/5; implemented in `src/parse/drawing.rs` (`group_stack: Vec<GroupContext>` in `parse_anchor_body`, and `resolve_grouped_pic`, called once per `</xdr:pic>`)

* **Details**: `parse_anchor_body` maintains `group_stack: Vec<GroupContext>`, pushed on every `<xdr:grpSp>` start and popped on its end, with **no depth limit** — the design doc states only that "the stack's own length is always the current nesting depth — no separate counter is needed," never that a maximum is enforced, and no such cap exists anywhere in `src/parse/drawing.rs` (confirmed by inspection: no `MAX_*` constant of any kind appears in that file, unlike `resolve/merge.rs`'s `MAX_MERGE_REGIONS` or `resolve/column_width.rs`'s `MAX_COLUMN_WIDTH_RANGES`, which the design docs for those files document and cap explicitly).

  `resolve_grouped_pic(group_stack, ..)` is called once for every `</xdr:pic>` closing tag found anywhere inside the group tree (`src/parse/drawing.rs` line ~194), and its cost is **O(current nesting depth)** — it iterates the *entire* `group_stack` in reverse, applying each level's linear transform (`docs/design/parse/drawing.en.md`'s own description: `child' = off + (child - chOff) * (ext/chExt)`, applied "from innermost to outermost"). Because `<xdr:grpSp>` can contain any number of sibling `<xdr:pic>` elements at any depth, and DrawingML places no schema-level limit on nesting depth, a single drawing part can contain `D` levels of nesting with `N` sibling pictures at the innermost level, at which point total parsing cost is **O(N × D)** — while the XML byte cost of constructing such a file is only **O(N + D)** (additive, not multiplicative). This is exactly the shape of the previously-fixed merge-cell finding (`docs/security/old/code-review.en.md` Finding 1: an O(N²) cost hiding behind a byte-size cap that doesn't bound N) — except here the multiplication is between two independently-cheap-to-inflate axes (depth and sibling count) rather than a single count squared against itself, and unlike the merge-cell case, **no defensive cap of any kind was ever added** for either axis.

* **Empirical confirmation**: I added a temporary, `#[ignore]`d unit test directly calling `parse_drawing` (the same pure-XML-parsing entry point the design doc describes) with synthetically generated `<xdr:grpSp>` nesting and sibling `<xdr:pic>` counts, then reverted it (no residual change left in the working tree — see `src/parse/drawing.rs` git history is clean). Measured on the current `master` build (release profile, Apple-class hardware, single-threaded):

  | Nesting depth (D) | Pictures at innermost level (N) | XML size | Elapsed |
  | ---: | ---: | ---: | ---: |
  | 100 | 100,000 | 29.8 MB | 191 ms |
  | 100,000 | 100 | 15.5 MB | 193 ms |
  | 5,000 | 5,000 | 2.26 MB | 135 ms |
  | 20,000 | 2,000 | 3.69 MB | 222 ms |
  | 50,000 | 1,000 | 8.0 MB | 325 ms |
  | 100,000 | 5,000 | 17.0 MB | **2.33 s** |
  | 50,000 | 50,000 | 22.6 MB | **10.9 s** |

  The first two rows (large N with small D, or large D with small N — i.e. either axis alone) stay cheap, confirming the cost really is the *product* of the two axes, not either one individually. The last two rows show that a file of just 17–23 MB — trivially far under both the 512 MiB per-entry Zip Bomb cap and the 2 GiB cumulative cap (`container/sanitize.en.md`'s `DEFAULT_MAX_UNCOMPRESSED_SIZE`/`DEFAULT_MAX_TOTAL_UNCOMPRESSED_SIZE`), and requiring no unusually large workbook by any other existing metric — already produces multiple seconds of fully synchronous CPU blocking inside `parse_drawing`, called from `pipeline.rs`'s Phase 3.5 during ordinary `parse_workbook`/`parse_workbook_reader` execution. Extrapolating the same square-law growth the merge-cell finding measured, a drawing part in the 50–100 MB range (still far under the per-entry cap) would very plausibly reach tens of seconds to minutes, i.e. the same severity class as the original merge-cell finding, before it was fixed.

* **Partial mitigating factor**: `group_stack` is an explicit heap-allocated `Vec`, not native call-stack recursion, so unlike a naive recursive-descent XML-nesting parser, there is no stack-overflow risk from depth alone — the cost is CPU time (and, secondarily, the `Vec<GroupContext>`'s own heap growth, negligible next to the CPU cost). This is a real point in the design's favor and is noted under Design Judged Sound, but it does not change the CPU-exhaustion analysis above.

* **Risk scenario**: An attacker submits an `.xlsx` (or any system that calls `parse_workbook`/`parse_workbook_reader` on untrusted input, e.g. a document-upload feature) containing a `drawingN.xml` with a deeply nested `<xdr:grpSp>` tree and a modest number of sibling pictures at the innermost level — a file in the tens-of-MB range, well within every documented and enforced size/count limit, that passes every existing check (Zip Bomb, Zip Slip, XXE, `MAX_MERGE_REGIONS`, `MAX_COLUMN_WIDTH_RANGES`) without triggering any of them. The calling thread (typically a web server's request handler) blocks for seconds to potentially minutes inside `parse_drawing`. A handful of concurrent requests using this shape would exhaust a thread/worker pool, exactly matching the risk-scenario framing of the original merge-cell finding.

* **Resolution**: Implemented exactly as recommended. `src/parse/drawing.rs` now defines `pub(crate) const MAX_GROUP_NESTING_DEPTH: usize = 64`, checked inside `parse_anchor_body`'s `b"grpSp"` start-tag arm — a nested group's start tag that would push `group_stack` past the limit returns the new `Error::TooManyNestedGroups { path, depth, limit }` ([`src/error.rs`](../../src/error.rs), mirroring `Error::TooManyMergedRanges`/`Error::TooManyColumnWidthRanges`'s shape) immediately, before any further nested content is read.

  A second, related cap was added at the same time: `resolve_grouped_pic`'s final resolved `(x, y, cx, cy)` is now checked for `is_finite()` and against a defensive plausibility ceiling (`MAX_PLAUSIBLE_EMU = 10^12`, ~27.7 km — several orders of magnitude beyond Excel's real maximum sheet extent), returning `Error::InvalidPackage` on either failure — closing a related, smaller-scale issue where a handful of nesting levels with an extreme `ext`/`chExt` ratio could drive the resolved coordinate to `f64::INFINITY` (silently saturating to `i64::MAX` via Rust's saturating float-to-int cast) well before `MAX_GROUP_NESTING_DEPTH` would ever be reached — see [`code-review.en.md`](code-review.en.md) Finding 2 for full detail on this second issue.

  Regression tests were added to `src/parse/drawing.rs`: `group_nesting_depth_at_the_limit_is_accepted`/`group_nesting_depth_over_the_limit_is_too_many_nested_groups` cover the exact 64/65 boundary (following `resolve/merge.rs`'s `region_count_at_the_limit_is_accepted`/`region_count_over_the_limit_is_too_many_merged_ranges` pattern), and `extreme_group_transform_scale_is_rejected_as_invalid_package` covers the second issue.

  Re-measuring the exact attack shape from the table above after the fix (same D=100,000/N=100 shape that previously ran unbounded): **rejected in under 1ms**, since the depth check now fires at nesting level 65, long before any of the O(N × D) transform work would run.

  `docs/design/parse/drawing.en.md`'s Error Handling Policy, Testing Strategy, and Open Questions (new item 7) were updated to document both caps.

### Finding 2: Several design docs' "Key Types" code blocks were not updated when the features their own prose describes were implemented, undermining a documentation-only security review's ability to verify newly added numeric fields

* **Severity: Low (documentation/process gap, not itself a vulnerability)**
* **Location**: [`model/sheet.en.md`](../design/model/sheet.en.md) (the "Key Types" code block, lines 14–240, has no `Image`/`ImageAnchor`/`AnchorMarker`/`ImageExtent`/`ColWidthRange` definitions, even though the "Feature: images (Issue #65)" and "Feature: column width (Issue #39)" prose sections immediately below it, and the Dependencies section, discuss them at length); [`json.en.md`](../design/json.en.md) (the "Key Types" code block has no `images`/`columns` serialization code — no `JsonImage`/`JsonImageAnchor`/`JsonAnchorMarker` type and no `state.serialize_field("images", ..)` call — even though its own Dependencies section explicitly lists `Sheet::images`, `Image`, `ImageAnchor`, `AnchorMarker` as things it depends on, and its Testing Strategy has a dedicated bullet for how `images` must serialize); [`model/mod.en.md`](../design/model/mod.en.md) (its re-export list, `pub use sheet::{MergedRegion, Sheet, SheetVisibility};`, omits `ColWidthRange`, `Image`, `ImageAnchor`, `AnchorMarker`, `ImageExtent` — all of which exist in `src/model/sheet.rs` today per `json.en.md`'s own Dependencies claim, `crate::model::{ColWidthRange, Sheet}`, used by `resolve/column_width.en.md`)

* **Details**: This project's stated process (per the user's own standing instruction) is design → implementation → test, with `docs/design/` actively kept in sync after each feature lands — and for the most part this held up extremely well across this review (every Issue #37/#38/#39/#40/#41/#42/#65/#67/#75 left detailed, implementation-accurate prose behind, including exact struct/field names, error variants, and even measured benchmark numbers). But the actual Rust struct definitions for `AnchorMarker { cell, col_off: i64, row_off: i64 }` / `ImageExtent { cx: i64, cy: i64 }` / `ImageAnchor` / `Image` — all of which hold attacker-controlled numeric data read from `drawingN.xml` and propagated straight through to the public JSON output — exist in `src/model/sheet.rs` (confirmed by direct inspection) but are never shown in `model/sheet.en.md`'s own "Key Types" code sample, only described in prose. The same gap exists for how `Sheet::images`/`col_width_ranges` actually get serialized in `json.rs`.

  This matters for a review like this one specifically because Finding 1 concerns exactly this kind of newly-added numeric/nesting logic — a reviewer working strictly from the design docs' code samples (as this review's brief requested) has no way to see the `i64` EMU fields' bounds-checking policy (there is none documented, and in fact none enforced beyond ordinary `i64` parse success — see the note below) or the `group_stack`/`resolve_grouped_pic` shape at all without reading the prose section by section, rather than the "Key Types" block a reviewer would normally treat as the authoritative interface summary. It is likely not a coincidence that Finding 1's gap and this documentation gap sit in the same module.

  Separately, and not risky enough to itself warrant a finding: `AnchorMarker::col_off`/`row_off` and `ImageExtent::cx`/`cy` (EMU units) are parsed via `parse_attr_i64` (confirmed in `src/parse/drawing.rs`) with no range check beyond "parses as `i64`" — an attacker can set `cx="9223372036854775807"` and it will propagate unchanged through to the JSON output as a plain integer. `serde_json` renders large `i64` values as literal integers (not scientific notation), which a JavaScript `JSON.parse` consumer would silently lose precision on past 2^53 — a data-fidelity footgun for downstream consumers, not a vulnerability in this library (no internal computation in `resolve_grouped_pic` can overflow from this, since the scale factors are computed in `f64`), and arguably in scope of the same design tradeoff `model::CellRef`'s row/col bounds-checking already addressed for a different field (`docs/security/old/code-review.en.md` Finding 2) — but currently undocumented in `model/sheet.en.md`'s Open Questions.

* **Risk scenario**: Not directly exploitable on its own. The risk is process/verifiability: a future design-only security review (or a new contributor implementing a related feature) reading `model/sheet.en.md`'s or `json.en.md`'s code samples in isolation would reasonably conclude those samples are a complete and current picture of the relevant types, and could miss exactly the kind of gap Finding 1 describes.

* **Recommendation**: Backfill the `Image`/`ImageAnchor`/`AnchorMarker`/`ImageExtent`/`ColWidthRange` struct definitions into `model/sheet.en.md`'s "Key Types" code block (they can be copied close to verbatim from `src/model/sheet.rs`, which is already fully implemented and stable), add the corresponding `images`/`columns` serialization code to `json.en.md`'s "Key Types" block, and add the missing types to `model/mod.en.md`'s re-export list to match `src/model/mod.rs`'s actual re-exports. While doing so, add a line to `model/sheet.en.md`'s Open Questions noting the EMU fields' lack of a magnitude bound and the resulting large-integer JSON precision caveat, even if the conclusion is "accepted, not a vulnerability" (matching how `docs/security/old/code-review.en.md` Finding 2 was handled for `CellRef`).

## Design Judged Sound (not counted as findings, but documented with rationale)

* **XXE / Zip Bomb / Zip Slip mitigation extended cleanly to every new module** ([`parse/drawing.en.md`](../design/parse/drawing.en.md), [`parse/styles.en.md`](../design/parse/styles.en.md), [`pipeline.en.md`](../design/pipeline.en.md) Phase 3.5): both new `parse/` modules construct their `Reader` only via `create_secure_reader` and read events only via `read_event` (confirmed against each file's own "Key Types" code and Error Handling Policy sections, which explicitly cite "Structurally invalid XML converts to `Error::XmlParse`/`Error::ZipBombDetected`/`Error::DoctypeRejected` via the same `create_secure_reader`/`read_event` gateway every `parse/` module uses" for `drawing.en.md`, and the equivalent for `styles.en.md`). `pipeline.en.md`'s Phase 3.5 locates and reads `drawingN.xml`/`drawingN.xml.rels` through the same `container::get_entry`/`parse::parse_relationships` gateway every other OPC part uses, and checks an `Internal` image target's mere existence via `container::ZipContainer::has_entry` (added specifically to avoid an unnecessary `get_entry`/`BoundedReader` construction for a caller that never reads the bytes) without ever bypassing `validate_entry_path`'s re-validation. No new design doc describes or implies a parallel, less-guarded read path.
* **`resolve_grouped_pic`'s `chExt=0` divide-by-zero guard** ([`parse/drawing.en.md`](../design/parse/drawing.en.md) Error Handling Policy, confirmed in `src/parse/drawing.rs`'s `resolve_grouped_pic`): exactly the kind of numeric-safety check this review was asked to look for and confirm — `scale_x = ext_cx / ch_ext_cx` is guarded by an explicit `Error::InvalidPackage` fail-fast on `ch_ext_cx == 0 || ch_ext_cy == 0`, checked before either division executes, consistent with the file's stated general policy of "rejecting a well-formed-but-nonsensical numeric value rather than silently producing `NaN`/`Infinity`."
* **The previous review's open date-format-heuristic ReDoS concern is fully closed at the implementation level** ([`parse/styles.en.md`](../design/parse/styles.en.md) `is_date_time_format`, Open Question 2; `docs/security/old/design-review.en.md` Finding 4): confirmed directly in `src/parse/styles.rs::contains_date_time_token` — a single-pass `Chars` scan with no backtracking of any kind (bracket/quote/backslash-escape handling is a forward-only `for`-loop over the same iterator, never re-scanning), not a regex. The design doc's own Open Question 2 remains open only on classification *precision* (false positive/negative rate), not on the complexity question the old finding raised — worth a short doc note cross-referencing this resolution explicitly, but not a live risk.
* **`resolve::column_width`'s adoption of the merge-cell finding's lesson, even where its own algorithm didn't need it** ([`resolve/column_width.en.md`](../design/resolve/column_width.en.md) "Relationship to `resolve/merge.rs`" and Design history sections): despite `resolve/column_width.rs`'s 1D-interval overlap check having no O(N²)/O(N³) risk of its own (sorting once and checking only adjacent pairs is sufficient), the design doc explicitly caps the range count (`MAX_COLUMN_WIDTH_RANGES = 2,000`) for the same reason `MAX_MERGE_REGIONS` exists — "the file format doesn't stop you from doing it [is not] the same as doing it is free" — a direct, well-reasoned application of the prior review cycle's lesson to new code, and exactly the kind of defensive-cap thinking Finding 1 shows is still not applied uniformly everywhere it should be.
* **Consistent fail-closed / graceful-degradation split across `parse/drawing.rs` and `parse/styles.rs`** ([`parse/drawing.en.md`](../design/parse/drawing.en.md), [`parse/styles.en.md`](../design/parse/styles.en.md) Error Handling Policy sections): both new modules apply the same two-tier policy already established elsewhere in the project — a genuinely broken document (missing required element, unparseable numeric attribute, structurally invalid XML) is rejected with a typed `Error`, fail-fast; a semantically ambiguous but well-formed value (an unresolvable `numFmtId`/`fontId`/`fillId`/`theme`/`indexed` reference in `styles.xml`, an anchor with no picture) degrades gracefully to a documented default rather than erroring. Neither module introduces a third, inconsistent policy, and neither panics on malformed input by design (confirmed against each file's explicit "never panics" / "no `panic`" statements).
* **`Sheet::finalize_merges`'s sweep-line fix holds up as the right fix for the right layer** ([`model/sheet.en.md`](../design/model/sheet.en.md) "Fix: `finalize_merges`", [`resolve/merge.en.md`](../design/resolve/merge.en.md) Open Question 2's second addendum): this review re-confirms (rather than re-litigates) that Issue #43's fix correctly targeted `Sheet::get`/`iter_cells`'s per-cell resolution cost (the actual O(cells × merged regions) hazard), not `resolve/merge.rs`'s own already-capped O(N²) validation loop — the design doc's own account of three simpler, measured-and-rejected alternatives (a global cutoff, row bucketing, an interval tree) before landing on the sweep line is a good model of the "measure, don't guess" discipline this project applies, one Finding 1 shows should now be pointed at grouped-image nesting too.

## Out of Scope

* Supply-chain/dependency vulnerabilities in `quick-xml`, `zip`, `serde`/`serde_json`, or `thiserror` — out of scope, consistent with the prior reviews.
* Pure code-quality/architecture concerns with no security manifestation (e.g. whether `Relationship.rel_type` should become an `enum`, `model/workbook.md`'s linear sheet-name lookup, MSRV policy) — several such Open Questions remain across the design docs but none of them bear on Zip Bomb/Zip Slip/XXE, algorithmic complexity under attacker control, unchecked numeric propagation, or fail-closed consistency, so they are not covered here.
* Findings already resolved by the prior two reviews and unchanged since (XXE's `read_event` gate, Zip Bomb's `SizeLimits`/`BoundedReader`, the CSV/formula-injection README warning, and the merge-cell O(N²) fix itself) are not re-litigated — see the Overall Assessment for how each was re-confirmed to still hold across the newly added modules, without repeating the original analysis.
* `docs/design/container/sanitize.en.md` Open Question 4 (compression-ratio-based early screening) and Open Question 5 (allowlist vs. denylist entry-name validation) remain open exactly as the first review left them, with no new information bearing on either since 2026-08-17 — not re-assessed here.
* Whether `Image::hyperlink` should also surface a group-level (rather than only per-picture) hyperlink, `editAs` anchor-behavior attributes, and other pure-fidelity Open Questions in `parse/drawing.en.md` — no security manifestation.
* A full line-by-line audit of `src/` is out of scope for this design-doc-focused review (Finding 1 was spot-checked and empirically measured specifically because the design doc's own prose made a checkable claim about an absent bound; this should not be read as a substitute for a dedicated code-level review of the newly implemented modules, which is assumed to be happening in parallel).
